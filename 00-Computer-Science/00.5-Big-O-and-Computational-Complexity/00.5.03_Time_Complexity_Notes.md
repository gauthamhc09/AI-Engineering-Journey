# Module 00.5.03 — Time Complexity

## Learning goal

Understand how the computational work performed by an algorithm changes as its input size grows. These notes summarize the concepts covered so far in the Computer Fundamentals learning sequence.

## 1. What is time complexity?

**Time complexity describes how an algorithm's computational work grows as its input size increases.**

It does not directly tell us the exact number of seconds a program takes to run.

For example, searching a list may require very little work if the target is at the beginning, but more work if the target is at the end or absent.

## 2. Input size and operation counting

Let `n` represent the size of the input. For a list, `n` commonly means the number of elements.

```python
def calculate_total(numbers):
    total = 0

    for number in numbers:
        total += number

    return total
```

Assuming each addition takes constant time for the values being processed:

- Initialization happens once.
- The loop processes each of the `n` elements.
- The return happens once.

A simplified operation-count model is:

\[
T(n) = n + 2
\]

This is an illustrative count of meaningful operations, not an exact count of CPU instructions or elapsed time.

**Key idea:** identify which operations depend on input size and which occur a fixed number of times.

## 3. Sequential loops

```python
for item in items:
    process(item)

for item in items:
    process(item)
```

Each loop executes `n` times, so the total number of calls to `process` is:

\[
T(n) = n + n = 2n
\]

The constant multiplier changes the amount of work, but the work still grows proportionally to `n`.

For example:
- 100 items → 200 calls
- 1,000 items → 2,000 calls

Two sequential loops do not automatically make an algorithm quadratic.

## 4. Nested loops

```python
for first in items:
    for second in items:
        process(first, second)
```

If both loops traverse all `n` items, the inner operation executes:

\[
T(n) = n \times n = n^2
\]

Examples:
- 3 items → 9 executions
- 100 items → 10,000 executions
- 1,000 items → 1,000,000 executions

If input size doubles, quadratic work grows by approximately four times:

\[
\frac{(2n)^2}{n^2} = 4
\]

**Important:** nested loops do not automatically imply `O(n²)`. Analyze what each loop actually iterates over and how the iteration counts depend on the input.

## 5. Nested loops with varying iteration counts

```python
for i in range(n):
    for j in range(i):
        process(i, j)
```

The inner loop executes a different number of times for each outer iteration.

For `n = 4`, the inner-loop execution counts are:

| Outer index `i` | Inner iterations |
|---:|---:|
| 0 | 0 |
| 1 | 1 |
| 2 | 2 |
| 3 | 3 |
| **Total** | **6** |

The total count is:

\[
T(n) = 0 + 1 + 2 + \cdots + (n-1)
     = \frac{n(n-1)}{2}
\]

This grows quadratically because the dominant term is proportional to `n²`.

The exact count differs from a full nested loop, even though both examples have quadratic growth.

## 6. Different input dimensions

Consider document processing:

```python
for document in documents:
    for chunk in document:
        process(chunk)
```

This does not automatically mean `O(n²)`. Let:
- `D` = number of documents
- `C` = average number of chunks per document

If every document has approximately `C` chunks, the work is proportional to `D × C`.

If `N` is the total number of chunks across all documents and each chunk is processed exactly once, the work is `O(N)`.

Always define what the input-size variable represents.

## 7. Early termination and input-dependent work

```python
def find_number(numbers, target):
    for number in numbers:
        if number == target:
            return True

    return False
```

The amount of work depends on where the target appears:

- Target at the beginning: one comparison.
- Target in the middle: several comparisons.
- Target at the end: up to `n` comparisons.
- Target absent: `n` comparisons.

The algorithm can terminate early, but its worst-case work still grows linearly with the list size.

Best-case, average-case, and worst-case analysis will be studied formally in Topic 12 of Module 00.5.

## 8. Time complexity vs. elapsed time

These concepts are related but distinct:

- **Input size:** how much data the algorithm receives.
- **Computational work:** the operations performed.
- **Execution time:** how long a particular run takes.

Two algorithms can both have linear growth yet run for different amounts of time.

For example:

```python
def sum_numbers(numbers):
    total = 0
    for number in numbers:
        total += number
    return total
```

```python
def print_numbers(numbers):
    for number in numbers:
        print(number)
```

Both traverse the list once under the usual assumptions, but printing may take substantially longer because it involves I/O and output handling. Buffering and the destination of output affect the actual cost.

Big O does not directly predict milliseconds. Actual performance can depend on:
- CPU and system load
- Programming language and runtime
- Memory access and cache behavior
- Input characteristics
- I/O and network latency
- Implementation details and constant factors

## 9. A systematic analysis method

When analyzing a program:

1. **Identify the input size.** State what `n` represents.
2. **Count important operations.** Separate fixed work from repeated work.
3. **Analyze control flow.** Consider sequential loops, nesting, conditions, and early returns.
4. **State assumptions.** For example, whether operations have constant cost and which execution case is being analyzed.
5. **Describe the growth.** Do not confuse a simplified operation count with actual runtime.

Example:

```python
def process(numbers):
    total = 0
    for number in numbers:
        total += number
    for number in numbers:
        total += number
    return total
```

A simplified count is:

\[
T(n) = 2n + 2
\]

The repeated work grows proportionally to `n`. Under usual assumptions, this is linear time complexity.

## 10. Why this matters in AI engineering

In document processing and RAG systems, different stages have different costs:

- Processing each document or chunk once may scale linearly with the number of items, assuming roughly constant work per item.
- Comparing every chunk against every other chunk can require quadratic work.
- An index can reduce the work needed for some lookups, at the cost of extra memory and maintenance.
- Embedding generation may be dominated by model inference, batching, and hardware.
- Individual database or network requests can add substantial latency even when each record is processed once.

Complexity helps reason about scaling; profiling and measurements help identify real bottlenecks. Not every database query or vector-search implementation has one universal complexity.

## Key takeaways

- Time complexity describes how computational work grows with input size.
- Input size must be defined clearly.
- Sequential loops add their work; two full passes produce `2n` iterations.
- Two nested loops each traversing `n` items can produce `n²` executions.
- Nested loops do not automatically mean quadratic growth; analyze actual iteration counts.
- Early termination can reduce work for some inputs, while worst-case work may still be large.
- The same asymptotic growth class does not guarantee the same elapsed time.
- Time and space complexity are different; more computational work does not automatically imply more memory use.
- Complexity analysis and real-world profiling complement each other.
