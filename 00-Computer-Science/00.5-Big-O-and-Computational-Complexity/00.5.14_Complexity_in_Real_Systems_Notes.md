# Module 00.5.14 — Complexity in Real Systems

## Big O is not the whole story
Big O describes how computational work grows with input size, not exact elapsed time. Two algorithms in the same complexity class can have different runtimes because of:
- Constant factors and implementation details.
- CPU instruction costs and hardware.
- Cache and RAM access patterns.
- Memory allocation and data layout.
- Database, disk, and network I/O.
- Serialization and external service calls.

## Constant factors
Two algorithms can both be `O(n)` but do different amounts of work per item. Processing each item once and performing a fixed 100 operations per item are both `O(n)`, but the latter may take substantially longer.

## Hardware and memory
- CPU operations have different costs.
- Cache hits are generally faster than fetching data from main memory.
- Data layout and access patterns can affect runtime without changing asymptotic complexity.

## Network latency and database calls
Fetching each document with a separate sequential request makes `n` database calls:

```python
for document_id in document_ids:
    document = fetch_document_from_database(document_id)
```

Round-trip latency and per-request overhead may dominate execution time. A batch query can retrieve multiple documents in one request:

```python
documents = fetch_documents_from_database(document_ids)
```

Batching can reduce network round trips significantly. The database still needs to locate and return records; exact complexity depends on indexes, query plans, implementation, and data size. Both approaches may involve `O(n)` overall work.

## AI engineering performance considerations

| Operation | Potential bottlenecks |
|---|---|
| Document chunking | Document count and size |
| Embedding generation | Model computation, hardware, batch size |
| Retrieval | Index strategy, database query, network latency |
| Reranking | Candidate count and model cost |
| LLM calls | Token counts, model latency, network overhead |
| API response | Database access, serialization, network |

A Python loop's complexity does not capture the full cost of model inference or remote API calls. Batching can improve throughput, depending on the system and workload.

## Practical performance workflow
1. **Measure** the operation under a representative workload.
2. **Profile** to identify where time and memory are spent.
3. **Diagnose** whether the bottleneck is CPU, memory, database, network, or model inference.
4. **Optimize** the relevant part: algorithm, batching, indexing, caching, or resource usage.
5. **Measure again** to verify improvement and preserve correctness.

## Key takeaways
- Big O describes growth, not exact seconds.
- Constant factors and system behavior can matter greatly.
- Repeated network round trips can dominate an otherwise linear task.
- Batching reduces request overhead but does not eliminate underlying database work.
- Measure before optimizing, then measure again.
