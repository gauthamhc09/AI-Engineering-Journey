# Module 00.6.07 — Hash Tables

## 1. Why hash tables?
Suppose an application stores 200,000 documents and frequently retrieves one by exact ID. Searching a list one record at a time takes O(n) time in the worst case. A hash table can usually locate a value by key in O(1) average time.

A **hash table** stores key-value entries and uses a hash function to help locate entries efficiently. Python's `dict` and `set` use hash-table-based implementations.

## 2. The basic lookup model
```text
Key → hash function → hash value → table lookup → candidate key/value
```
A simplified table might calculate:
```text
index = hash_value % capacity
```
This is an illustrative model. Python dictionaries use a more sophisticated implementation involving probing and resizing, not just this formula. The hash value guides lookup; it does not itself contain or return the associated value.

## 3. Hash functions
A hash function converts a key into an integer hash value:
```python
print(hash("apple"))
print(hash(42))
print(hash((10, 20)))
```
Exact values are not generally important. Python string hashes are randomized between processes by default, so a string's hash may differ across separate program runs.

Useful properties:
- Hashing should be reasonably fast.
- A key's hash must remain stable while it is used as a key.
- Equal keys must have equal hash values.
- Good distribution helps reduce collisions.

## 4. Collisions and equality
A **collision** occurs when different keys map to the same hash-table location. Different keys can also have the same hash value.

- Equal keys must have equal hashes.
- Equal hashes do **not** imply equal keys.
- The table uses key equality when necessary to distinguish candidate entries.

Python dictionaries use open addressing and probing to resolve collisions. Other hash-table designs may use separate chaining. Collisions are normal; good distribution and collision handling help maintain performance.

## 5. Time complexity
| Operation | Typical/average | Worst case |
|---|---:|---:|
| Lookup by key | O(1) | O(n) |
| Insert | O(1) amortized on average | O(n) |
| Delete by key | O(1) average | O(n) |
| Search an unsorted list | O(n) | O(n) |

O(1) is an average-case expectation, not a guarantee for every operation. Severe collisions can degrade performance. A resize can make an individual insertion expensive, even though insertions are typically amortized O(1) under ordinary assumptions.

## 6. Resizing
As a hash table grows, it may allocate a larger table and reorganize entries. This helps keep the table from becoming too crowded. A resize can take O(n) for that particular operation. Amortized analysis explains why a sequence of insertions can still have O(1) amortized insertion cost under typical assumptions.

## 7. Hashability in Python
Dictionary keys and set elements must be hashable. Hashability requires a stable hash and equality behavior consistent with hash-based collections.

```python
data = {
    "name": "Rahul",
    42: "answer",
    (10, 20): "coordinate"
}
```
Lists are mutable and unhashable, so they cannot be dictionary keys:
```python
data = {[10, 20]: "coordinate"}  # TypeError
```
A tuple is hashable only if all its elements are hashable. A tuple containing a list is also unhashable.

## 8. Dictionaries and sets
- **Dictionary (`dict`):** Maps unique keys to values.
- **Set (`set`):** Stores unique hashable elements and supports efficient membership checks.

```python
metadata = {"DOC-101": {"title": "Memory"}}
print(metadata["DOC-101"])

processed_ids = {"DOC-101", "DOC-102"}
print("DOC-102" in processed_ids)  # True
```

## 9. AI engineering applications
- **Document metadata:** Map document IDs to metadata for exact-key retrieval.
- **Caching:** Map request keys to previously computed results. A production cache also needs expiration/eviction policies.
- **RAG pipelines:** Map chunk IDs to source references or document metadata.
- **Backend applications:** Use dictionaries for configuration and intermediate data.

A hash table supports exact-key lookup; it does not perform semantic similarity search over embeddings. A vector index solves a different retrieval problem. An in-memory Python dictionary is also not automatically persistent or shared among multiple server processes.

## Key takeaways
1. Hash tables use keys and hash functions to locate entries efficiently.
2. Lookup, insertion, and deletion are typically O(1) on average.
3. Collisions are normal; equal hashes do not imply equal keys.
4. Equal keys must have equal hashes.
5. Resizing helps performance but can make an individual operation expensive.
6. Python dictionaries and sets use hashing.
7. Hash tables support exact-key lookup, not semantic vector search.
