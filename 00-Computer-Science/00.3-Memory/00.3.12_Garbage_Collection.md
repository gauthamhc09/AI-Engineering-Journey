# 00.3.12 — Garbage Collection

## Reachability
An object is **reachable** if the program can access it through references starting from live roots such as active variables, runtime structures, or other reachable objects. If no path remains, it is unreachable and can be reclaimed. Becoming unreachable and memory being reclaimed are related but not necessarily instantaneous.

## Reference counting in CPython
CPython tracks references to most objects. When an object's reference count reaches zero, it is normally deallocated promptly.

```python
a = [10, 20, 30]
b = a
del a
print(b)  # [10, 20, 30]
```
`del a` removes the name; it does not necessarily destroy the list because `b` still refers to it.

## Circular references
Two lists can refer to each other:
```python
a = []
b = []
a.append(b)
b.append(a)
del a
del b
```
Each list may keep the other's reference count above zero even though neither is reachable from those names. Reference counting alone cannot reclaim such a cycle. CPython's cyclic garbage collector can reclaim certain unreachable cycles of container objects.

## Two mechanisms
- **Reference counting:** deallocates objects when the count reaches zero.
- **Cyclic garbage collector:** detects certain unreachable reference cycles.

## Limits
A global list or cache can keep objects reachable even when the application no longer needs them. Garbage collection generally cannot infer that those references are unnecessary. Reclaimed memory also may not be returned to the OS immediately; an allocator may keep it for reuse.

## Misconceptions
`del name` always destroys the object — no. All GC is based on zero references — no. GC prevents every leak — no. Freed objects always reduce process memory immediately — no.
