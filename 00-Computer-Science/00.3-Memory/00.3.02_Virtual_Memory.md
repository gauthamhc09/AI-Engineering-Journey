# 00.3.02 — Virtual Memory

## 1. Why virtual memory exists

A process needs memory for code, variables, objects, stack, heap, and other runtime state. Physical RAM is finite and is shared by the operating system and running processes.

If ordinary programs used arbitrary physical addresses directly, several problems would arise:

- The system would have to manage physical placement directly for every program.
- One process could potentially access or overwrite another process's memory.
- Programs would be more dependent on the machine's physical memory layout.

The system needs a way to give processes manageable memory views and control which physical memory they can access.

## 2. The central idea

Instead of treating a program's address as a direct physical RAM address, virtual memory introduces an address-translation layer.

```text
Process
   ↓
Virtual address
   ↓
Address translation
   ↓
Physical address
   ↓
Physical RAM
```

A process uses addresses in its **virtual address space**. The system arranges for valid virtual addresses to map to physical memory, with access controlled by memory-management mechanisms.

## 3. What is a virtual address space?

A **virtual address space** is the range of virtual addresses available to a process, together with the system's rules for mapping and protecting those addresses.

Conceptually, two processes each have their own address space:

```text
Process A                         Process B
Virtual address space             Virtual address space
0                                 0
1                                 1
2                                 2
...                               ...
```

The diagrams are simplified. Real address spaces are large and contain regions with different purposes and permissions.

## 4. The same virtual address can mean different things

Two processes can use the same numerical virtual address while that address maps to different physical locations.

For example:

```text
Process A:
Virtual address 1000 → Physical address 5000

Process B:
Virtual address 1000 → Physical address 9000
```

The meaning of a virtual address depends on the address space in which it is used. Therefore, the same virtual address in two different processes does not necessarily identify the same physical memory.

## 5. How virtual memory supports isolation

Suppose Process A and Process B have different mappings:

```text
Process A
Virtual 1000 ─────→ Physical 5000

Process B
Virtual 1000 ─────→ Physical 9000
```

Process A's virtual address `1000` refers to its mapped location, while Process B's virtual address `1000` refers to its own mapped location.

The operating system configures memory-management structures and permissions, and hardware enforces the mappings during memory access. A normal application cannot simply use an arbitrary physical address as though it were an ordinary address in its own virtual address space.

This is a major foundation of **process memory isolation**. It is not the only security mechanism in an operating system, but it is an essential one.

## 6. What happens during a memory access?

At a high level:

```text
Program executes a memory-accessing instruction
        ↓
Instruction uses a virtual address
        ↓
Memory-management hardware translates/checks it
        ↓
A physical address is used for the memory access
        ↓
Data is read or written, if access is valid
```

The Memory Management Unit (MMU) is hardware involved in address translation and protection. The operating system establishes and manages the structures and permissions used by this hardware.

We will study the details of virtual addresses, pages, page tables, and the MMU in their assigned later lessons. This note intentionally keeps those mechanisms at a high level.

## 7. Virtual memory is not simply swap

A common misconception is:

> Virtual memory means using an SSD as extra RAM.

That is not the core definition.

Virtual memory provides virtual address spaces and controlled mapping from virtual addresses to physical memory. Operating systems may also use storage as backing for some memory contents, but that is a related capability rather than the fundamental meaning of virtual memory.

For this module, keep these ideas distinct:

- **Virtual address space:** the addresses a process uses.
- **Address translation:** the mechanism that maps virtual addresses to physical addresses.
- **Memory protection:** controls that restrict which memory a process can access.
- **Paging to storage:** an additional mechanism that may be used by an operating system.

## 8. A simplified numerical example

Imagine a simplified machine with physical locations numbered `0` through `9`.

Process A has these mappings:

```text
Virtual 0 → Physical 4
Virtual 1 → Physical 5
Virtual 2 → Physical 6
```

Process B has these mappings:

```text
Virtual 0 → Physical 7
Virtual 1 → Physical 8
Virtual 2 → Physical 9
```

Both processes can use virtual address `0`, but it maps to different physical locations for each process.

These numbers are illustrative only; actual systems use much larger address ranges and more sophisticated mappings.

## 9. Connection to operating-system concepts

The process abstraction gives each process its own virtual address space. This builds on the OS concept of memory isolation:

```text
Process
   ↓
Virtual address space
   ↓
Virtual addresses
   ↓
Controlled translation and protection
   ↓
Physical memory
```

The important question is no longer only “Where is the data in RAM?” It is also “Which virtual address is the process using, and how does the system map and protect it?”

## 10. Python connection

Consider:

```python
x = 42
```

Do not assume that the variable `x` directly identifies a physical RAM address. Python runs inside a process, and that process uses a virtual address space.

A high-level path is:

```text
Python program
      ↓
Python runtime and process memory
      ↓
Virtual address space
      ↓
Virtual address
      ↓
Address translation
      ↓
Physical memory
```

This is only the broad picture. The Python object model, references, and exact relationship between Python variables and objects will be covered later in this module.

## 11. AI engineering connection

A FastAPI application or Python worker runs as a process and uses its virtual address space for active code and data.

```text
FastAPI worker
      ↓
Python process
      ↓
Process virtual address space
      ↓
Memory-management hardware
      ↓
Physical RAM
```

This foundation will help explain later why multiple processes have separate memory views and why memory consumption matters when running workers or loading large objects and models. The detailed consequences depend on allocation, sharing, operating-system behavior, and runtime implementation, which we will study in later concepts.

## Key takeaways

- Physical RAM is finite and shared by the system.
- A process uses virtual addresses rather than normally addressing arbitrary physical RAM directly.
- Virtual memory introduces address translation between virtual and physical addresses.
- Each process has its own virtual address space.
- The same virtual address can map to different physical locations in different processes.
- Virtual memory is a key foundation for process memory isolation.
- The OS configures memory-management structures and permissions; hardware participates in translation and protection.
- Virtual memory is not synonymous with swap or using an SSD as extra RAM.
- Python code runs within a process's virtual address space; it does not normally work with physical RAM addresses directly.

## Common misconceptions

- **“Virtual memory is just swap.”** Virtual address spaces and address translation are fundamental even when discussing memory backed by physical RAM.
- **“The same virtual address means the same physical location.”** The mapping depends on the process's address space.
- **“A process can freely access any physical RAM address.”** Normal application code is constrained by virtual addressing and memory protection.
- **“The OS alone translates every memory access in software.”** The OS manages the relevant structures; hardware performs the ordinary translation and protection checks.
- **“A Python variable is a physical address.”** Python operates within a process and its virtual address space, with additional runtime/object-model layers.
