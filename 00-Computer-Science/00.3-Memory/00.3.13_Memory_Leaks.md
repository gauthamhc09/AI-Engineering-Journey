# 00.3.13 — Memory Leaks

## Definition
A memory leak occurs when a program retains memory it no longer needs, causing unnecessary memory use. In Python, this often happens because objects remain reachable through unintended or long-lived references.

A leak need not grow forever. It may stop at a limit or when a workload ends. Rising memory that later stabilizes does not automatically prove a leak.

## Example
```python
request_history = []

def process_request(data):
    request_history.append(data)
```
Every call adds a reference to `data`. If the global list is never cleared or bounded, objects remain reachable and memory use may grow.

Compare a temporary local object that has no remaining references after a function returns: it can be reclaimed. A global cache can retain objects; that is a leak if retention is unintended and unbounded.

## Common causes
- Unbounded global lists/dictionaries.
- Caches without size limits or eviction.
- Lingering references through callbacks, closures, handlers, or long-lived objects.
- Unreleased files/connections (resource leaks, which may or may not also be memory leaks).
- Native allocations not directly managed by Python's GC.

## Investigation
1. Measure memory before, during, and after representative workloads.
2. Repeat tests and see whether memory stabilizes.
3. Use `tracemalloc` snapshots to compare Python allocation sites.
4. Inspect collections and caches for accumulating objects.
5. If process memory grows but traced Python allocations do not, investigate native allocations and allocator behavior.

Process resident memory can remain high after Python objects are freed because the allocator may retain memory for reuse. `tracemalloc` does not capture all memory used by a process.

## AI/backend connection
A long-running FastAPI or RAG service might retain every retrieved document or request result in a global collection. Bounded caches, eviction policies, and removing unnecessary references can help.
