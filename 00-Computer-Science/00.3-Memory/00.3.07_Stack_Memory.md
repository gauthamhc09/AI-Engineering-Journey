# 00.3.07 — Stack Memory

## Why programs need a call stack
When one function calls another, the caller may wait and then resume after the called function returns. The program must preserve enough execution information to continue correctly.

A **call stack** tracks active function calls and the information needed to resume them.

## LIFO: Last In, First Out
A conventional call stack follows **LIFO** ordering: the most recently called function normally returns first.

```python
def main():
    print("A")
    calculate()
    print("C")

def calculate():
    print("B")

main()
```

Output:
```text
A
B
C
```

`main()` pauses while `calculate()` runs, then resumes after it returns.

## Stack frames
Each active call is typically associated with a **stack frame** in implementations using a conventional call stack. A frame can contain:
- Where execution should resume after return.
- Function-local execution state.
- Some local values or references, depending on implementation.
- Information needed to restore the caller's state.

Frame layout depends on the language, runtime/compiler, and calling convention.

## Nested calls and stack unwinding
If `first()` calls `second()`, which calls `third()`, then `third()` normally returns first. `second()` resumes and returns, followed by `first()`. Removing active call information as calls return is called **stack unwinding**.

## Python's call stack
Python tracks function calls and execution state, but its logical call stack is not necessarily identical to a native machine stack. In CPython, Python function execution uses interpreter-managed frames; the relationship to the native C stack depends on CPython version and execution path.

Do not assume every Python local variable physically lives on the machine stack.

## Key takeaways
1. A call stack tracks active calls and execution state.
2. Conventional nested calls follow LIFO ordering.
3. A stack frame holds information associated with an active call.
4. Returning lets the caller resume.
5. Python frames and the native machine stack are not necessarily identical.
6. Not every Python local variable or object should be assumed to live directly on the machine stack.
