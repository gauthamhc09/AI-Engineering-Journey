# Module 00.4.08 — Race Conditions

## What is a race condition?
A **race condition** occurs when the outcome depends on the timing or interleaving of concurrent operations.

It is not simply the fact that two threads access the same variable. Concurrent reads can be safe when the data is not being modified. The risk comes from operations that conflict or rely on assumptions that may become outdated.

## Example: lost update
```python
counter = 0

# Both threads perform:
counter += 1
```
A possible interleaving:
1. Thread A reads `counter == 0`.
2. Thread B reads `counter == 0`.
3. Thread A calculates and writes `1`.
4. Thread B calculates and writes `1`.

The final value is `1`, although two increments were attempted. This is a **lost update**.

The statement `counter += 1` looks like one line, but conceptually it involves reading, calculating, and writing. Another thread may run between those steps.

## A race does not require perfectly simultaneous writes
Two operations can interleave even if they do not execute at precisely the same instant. Their relative timing can still affect the result.

## Check-then-act race
```python
if balance >= amount:
    balance -= amount
```
If two threads check the balance before either deducts money, both may decide a withdrawal is allowed. One can then proceed using a check that is no longer valid. The check and update form one logical operation, but concurrent execution can separate them.

## Prevention
Synchronization mechanisms such as locks can coordinate access to shared state. Protection must cover the complete logical operation that needs to remain consistent.

## AI engineering connection
Concurrent updates to request counters, job status, or cache metadata can produce incorrect results if they are not coordinated.

## Key takeaways
1. Race conditions depend on timing/interleaving.
2. Concurrent reads alone are not automatically a race condition.
3. Lost updates are one common outcome.
4. Check-then-act logic may need to be protected as one operation.
