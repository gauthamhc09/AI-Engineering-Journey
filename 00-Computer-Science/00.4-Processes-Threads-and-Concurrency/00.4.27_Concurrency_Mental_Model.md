# Module 00.4.27 — Concurrency Mental Model

## The big picture
Threading, multiprocessing, and `asyncio` are related approaches for managing work, but they solve different execution problems. Choose based on what the workload spends time doing.

## Concurrency vs parallelism
- **Concurrency:** Multiple tasks make overlapping progress. They may take turns on one CPU core.
- **Parallelism:** Multiple tasks execute at the same time on separate execution resources, such as CPU cores.
A concurrent program is not necessarily parallel.

## Three common approaches

### 1. Threading
Multiple threads within one process can make progress concurrently. Threads are useful for I/O-bound work that uses blocking libraries, such as network requests or downloads.

In standard GIL-enabled CPython, threads generally cannot execute Python bytecode in parallel within the same interpreter. Blocking I/O operations commonly release the GIL while waiting, allowing other threads to make progress.

### 2. Multiprocessing
Separate processes ordinarily have separate virtual address spaces and Python interpreters. CPU-bound Python work can run in parallel across CPU cores when resources permit.

Processes can communicate using IPC mechanisms such as queues, pipes, or deliberately shared memory. A process pool reuses a bounded set of workers for many tasks.

### 3. `asyncio`
An event loop coordinates asynchronous tasks, often on a single thread. When a task awaits an incomplete asynchronous operation, it suspends and allows other ready tasks to progress.

`asyncio` is useful for many concurrent I/O operations when the libraries support asynchronous I/O. It does not automatically make CPU-heavy code or blocking functions non-blocking.

## Practical decision guide
| Workload | Common starting point | Reason |
|---|---|---|
| Network requests using blocking APIs | Threads or a thread pool | Other threads can progress during blocking I/O waits |
| Many concurrent requests with async-compatible libraries | `asyncio` | Coordinates many tasks without one thread per task |
| CPU-heavy pure-Python calculations | Multiprocessing | Separate processes can execute across cores |
| Large batches of independent CPU tasks | Process pool | Reuses workers and limits concurrent process count |
| GPU-based LLM inference | Depends on the inference stack | Batching, GPU utilization, native libraries, and serving architecture matter |

These are starting points, not universal rules. Native libraries may release the GIL, and performance depends on implementation, data movement, memory, and workload.

## FastAPI responsiveness
- Long blocking operations on the event-loop thread can delay other asynchronous tasks on that loop.
- Blocking I/O can be moved to a thread pool or replaced with async-compatible libraries.
- CPU-heavy pure-Python work may be better isolated in a process pool or separate worker service.
- Multiprocessing has costs, including startup, serialization/data transfer, memory, and worker management.

## AI engineering example: document/RAG pipeline
1. **Fetch documents:** threads or async I/O, depending on the client library.
2. **Parse and transform text:** consider a process pool if this stage is CPU-bound and parallelism is beneficial.
3. **Generate embeddings and index:** consider batching, an embedding service, or GPU resources as appropriate.
4. **Retrieve context and call an LLM:** asynchronous I/O can help coordinate external services.

The engineering skill is identifying the bottleneck and selecting an execution model, not memorizing a single tool.

## Core rules to remember
- Concurrency is overlapping progress; parallelism is simultaneous execution.
- Threads share process memory, so shared mutable state may need synchronization.
- Separate processes ordinarily isolate memory and require IPC to exchange data.
- The GIL affects Python-bytecode parallelism in standard GIL-enabled CPython, not every native/GPU operation.
- `asyncio` depends on cooperative asynchronous operations; a blocking call can stall the event-loop thread.
- More threads or processes do not automatically mean better performance.
