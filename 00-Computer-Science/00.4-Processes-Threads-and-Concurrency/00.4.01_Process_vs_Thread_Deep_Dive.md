# Module 00.4 — Processes, Threads, and Concurrency

# 00.4.01 — Process vs Thread: Deep Dive

## 1. Why processes and threads matter

An application may need to handle several tasks or requests while other tasks are still running or waiting. For example, a FastAPI AI application may need to:
1. Receive a user's question.
2. Query PostgreSQL.
3. Retrieve relevant chunks from a vector database.
4. Call an external LLM API.
5. Return a response.

Processes and threads are important building blocks for managing execution and making progress on multiple tasks.

## 2. Program, process, and thread

- **Program:** Instructions stored somewhere, such as on an SSD.
- **Process:** A running instance of a program, with its own execution environment and resources.
- **Thread:** An execution unit within a process.

A process has at least one thread. The operating system schedules threads for CPU execution.

## 3. What a process owns

A process has resources such as:
- **Virtual address space:** The memory environment in which the process operates.
- **Code and data:** Program instructions and global data.
- **Heap:** Memory used for dynamically allocated objects.
- **File descriptors or handles:** References to open files, sockets, and other resources.
- **At least one thread:** A path that executes instructions.

Processes normally have separate virtual address spaces. This protects one process's private memory from ordinary direct access by another process. It does not mean that every physical page or every OS-managed resource must be completely separate; some resources can be deliberately shared.

## 4. What a thread has

Each thread has its own execution state, including:
- **Program counter:** Identifies the next instruction to execute.
- **CPU register state:** The register values associated with the thread's execution.
- **Stack:** Holds function-call frames and associated execution data.

Threads in the same process generally share the process's code, global data, heap objects, and many process resources.

### Mental model

```text
Process A
├── Shared process environment
│   ├── Code and data
│   ├── Heap objects
│   └── Process resources
└── Thread A1
    └── Its own execution state and stack

Process B
├── Separate virtual address space
└── Thread B1
    └── Its own execution state and stack
```

This is a conceptual model; operating systems can share certain physical pages and kernel-managed resources.

## 5. Shared globals versus thread-local variables

### Case A: Threads in the same process

```python
counter = 0

# Thread A
counter = 10

# Thread B reads counter after Thread A's assignment has completed
```

If Thread A completes the assignment before Thread B reads the variable, and no other code changes it, Thread B reads `10`. Both threads can access the same process-level global variable.

**Key point:** Shared memory enables communication, but it does not automatically make every sequence of operations safe. Concurrent modifications can create race conditions, which we will study later.

### Case B: Separate processes

```text
Process A: counter = 10
Process B: counter = 0
```

Even if both processes use the name `counter`, their ordinary variable bindings exist in separate process memory environments. Changing Process A's variable does not automatically change Process B's variable.

Processes can communicate or share memory deliberately using mechanisms such as shared-memory regions and inter-process communication (IPC), which will be covered later.

### Case C: Local variables in a function

```python
def work():
    count = 0
    count += 1
    print(count)
```

When two threads independently call `work()`, each invocation has its own function-call frame and local binding for `count`. Each can print `1`; one invocation's local `count` does not automatically change the other's.

**Refinement:** Threads can share objects even when those objects are not global. An object can be shared through a function argument, an instance attribute, or another reference. The important question is whether threads access the same object or have separate local bindings—not simply where a variable is declared.

## 6. Process vs thread comparison

| Property | Threads in one process | Separate processes |
|---|---|---|
| Memory environment | Share the process's address space | Normally separate virtual address spaces |
| Global variables | Can access the same global binding | Normally independent bindings |
| Heap objects | Can access shared objects | Normally independent unless deliberately shared or communicated |
| Execution state | Each thread has its own | Each process has its own thread(s) and execution state |
| Communication | Shared objects can make communication convenient | Usually requires explicit IPC or shared memory |
| Isolation | Less isolated from other threads in the same process | Stronger memory isolation by default |

## 7. Python connection

```python
import threading
import multiprocessing

def work():
    print("Working")

thread = threading.Thread(target=work)
process = multiprocessing.Process(target=work)
```

These statements create objects representing a thread and a process; they do not start the work yet. Calling `start()` initiates execution.

- `threading.Thread` creates a thread in the current process.
- `multiprocessing.Process` starts a separate process with a separate process memory environment.

Python's exact behavior depends on its implementation and configuration. In particular, do not assume that multiple Python threads always execute CPU-bound Python code in parallel. CPython's Global Interpreter Lock (GIL) will be studied later.

## 8. AI Engineering connection

For a document-processing or RAG service:
- **One process with multiple threads:** Threads can conveniently access shared in-memory configuration or cache objects, but shared mutable state requires care.
- **Multiple processes:** Can provide stronger isolation and may allow CPU-bound work to use multiple CPU cores, but communication and data-transfer overhead may increase.
- **One thread in one process:** Simpler to reason about, but offers fewer execution paths for concurrent work.

The best design depends on the workload (CPU-bound or I/O-bound), runtime constraints, communication cost, failure isolation, throughput, and latency.

### Common misconceptions

- **Misconception:** Two threads in one process always execute simultaneously.  
  **Correction:** Simultaneous execution depends on CPU cores and runtime constraints.
- **Misconception:** Variables with the same name in two processes refer to the same storage.  
  **Correction:** Separate processes normally have independent memory environments.
- **Misconception:** Only global variables can be shared by threads.  
  **Correction:** Threads can share objects through references passed in arguments, attributes, globals, and other mechanisms.
- **Misconception:** Shared memory guarantees correctness.  
  **Correction:** Shared state can introduce race conditions and synchronization requirements.
